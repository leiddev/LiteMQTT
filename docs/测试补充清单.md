## T1 · 坏输入：parser 不校验长度（最高优先）

### 问题

`packets.hpp` 里所有 `parse()` 都是同一个模式：

```cpp
static connack_packet parse(const std::vector<uint8_t>& data) {
    buffer_reader reader(data);
    uint8_t packet_type_byte = 0;
    reader.read_uint8(packet_type_byte);        // 返回值忽略
    std::size_t remaining_len = 0;
    reader.read_remaining_length(remaining_len); // 返回值忽略
    connack_packet pkt;
    reader.read_uint8(pkt.session_present);      // 返回值忽略
    reader.read_uint8(pkt.return_code);          // 返回值忽略
    return pkt;                                  // 字段停在上一个值
}
```

`remaining_len` 读出来之后**从不**和 `data.size()` 比较。截断的包输入不会报错，而是返回结构体，其中部分字段是默认值、部分字段是旧值。调用方无法区分"解析成功"和"解析了一半"。

### 用例

写在新文件 `test/robustness_test.cc`，用 `TEST(ParseTruncated, ...)` 组织。

| 用例 | 输入 | 预期（当前行为，多数为"待修"） |
|---|---|---|
| ConnackEmpty | `{}` | 应报告失败；当前返回 `return_code == 0`，看起来像"连接成功" |
| ConnackOneByte | `{0x20}` | 应报告失败 |
| ConnackHeaderOnly | `{0x20, 0x02}` | 应报告失败；当前返回 `return_code == 0` |
| ConnackLengthMismatch | `{0x20, 0x05, 0x00, 0x00}` 声明 5 实际 2 | 应报告失败 |
| PublishNoTopicLength | `{0x30, 0x01, 0x00}` | 应报告失败 |
| PublishTopicLenOverflow | `{0x30, 0x05, 0x00, 0xFF, 'a'}` 声明主题 255 字节只有 1 | 应报告失败 |
| PublishQos1NoPacketId | QoS1 有主题无 packet id | 应报告失败 |
| PublishPayloadTruncated | 声明 100 字节负载实际 10 | 应报告失败 |
| SubackNoPacketId | `{0x90, 0x01, 0x00}` | 应报告失败 |
| SubackEmptyReturnCodes | 只有 packet id，无返回码 | 有歧义：可能是合法空 SUBACK，需明确语义 |
| PubackShort | `{0x40, 0x02, 0x00}` | 应报告失败 |
| UnknownPacketType | 固定头 `0x00` 或 `0xF0` | 应报告失败 |

### 需要改的库代码

把每个 `parse()` 改成返回 `bool`（或 `std::optional<T>`，但项目是 C++14 且不想引入新头文件，`bool` + 出参最贴合现有风格）：

```cpp
// packets.hpp
static bool parse(const std::vector<uint8_t>& data, connack_packet& out);
```

或在结构体里加一个 `bool valid` 成员，调用方检查。**推荐前者**，因为忘记检查 `valid` 不会编译报错，而忘记检查 `bool` 返回值可以靠 `/w4` 或 `-Wunused-result` 提示。

同时所有 `reader.read_xxx(...)` 的返回值都要检查，任一失败立即 `return false`。

`remaining_len` 必须校验：`remaining_len == data.size() - header_size`。`header_size` 是 1 加上 remaining length 字节数，`connection` 已经把它拼在 `read_header_` 里了，所以 `data.size() - read_header_.size()` 就是实际 body 长度。

## T2 · connection 分帧的异常路径

### 用例

`test/connection_test.cc`，沿用现有的 `loopback_broker`（**先修 T6 的问题**）。

| 用例 | 输入 | 预期 |
|---|---|---|
| RejectsReservedPacketType0 | peer 发 `0x00 0x00` | `read_handler` 收到 `asio::error::invalid_argument`，连接不再继续读 |
| RejectsReservedPacketType15 | peer 发 `0xF0 0x00` | 同上 |
| RejectsRemainingLength5Bytes | peer 发 `0x30 FF FF FF FF 7F` | `read_handler` 收到 `asio::error::message_size` |
| RejectsOversizedRemainingLength | peer 发 4 字节长度 = 268435455（协议上限） | 见下，当前会分配 256 MB |
| ClosesOnPeerReset | peer 发一半包后 `SO_LINGER` 0 强关 | `read_handler` 收到错误，不泄漏 |
| AcceptsZeroLengthBody | peer 发 `0xC0 0x00`（PINGREQ） | 正常返回 2 字节包 |

### 需要改的库代码

**必须改**，否则 `RejectsOversizedRemainingLength` 会真的分配 256 MB：

`inc/litemqtt/connection.hpp:230-259`，`read_packet_body()` 在 `std::make_shared<std::vector<uint8_t>>(remaining_length)` 之前要有个上限：

```cpp
// 256 KiB 是可配的；MQTT 默认无上限，但客户端需要一个保护值
static constexpr std::size_t kMaxPacketSize = 256 * 1024;
if (remaining_length > kMaxPacketSize) {
    reading_depth_ = 0;
    io_.post([handler]() {
        handler(asio::error::make_error_code(asio::error::message_size), {});
    });
    return;
}
```

建议做成 `connection` 的成员 `max_packet_size_` 加 setter，默认值定在 256 KiB 或 1 MiB。**这是个行为变更**：现有客户端能收任意大的包，加了上限后大消息会被拒。如果不想改行为，测试就只验证"不崩溃"，但那样这个用例的价值很低。

## T3 · 可注入的重传间隔（多项的前置条件）

> 已完成。`kPublishRetryInterval` 已删除，`retry_interval_` 与 `max_retransmits_` 成为成员，
> 两个重传计时器都改为读取它们。

### 问题

```cpp
// client.hpp:165 —— 声明了但从没被使用
static constexpr std::chrono::seconds kPublishRetryInterval{5};

// client.hpp:805 和 832 —— 各自硬编码 5 秒
timer->expires_after(std::chrono::seconds(5));
```

重传要等 5 秒、放弃要等 15 秒（3 次）。没有可注入的间隔，所有 QoS 1/2 重传测试都会慢到不可接受。

### 需要改的库代码

```cpp
// client.hpp，public 区
/// Test hook: override the retransmit interval used by the QoS 1/2 retry
/// timers.  Values below 1 ms are clamped; 0 restores the default.
void set_retry_interval_for_test(std::chrono::milliseconds interval) {
    retry_interval_ = (interval.count() < 0) ? std::chrono::milliseconds(5000) : interval;
}
```

把 `arm_publish_retry_timer` / `arm_pubrec_retry_timer` 里的 `std::chrono::seconds(5)` 换成 `retry_interval_`，删掉 `kPublishRetryInterval`（它现在就是死代码）。

这是**纯增量的私有钩子**，不影响任何现有行为。

## T4 · 出站 QoS 1 / QoS 2 的完整流程

> 已完成，见 `test/qos_test.cc`：下表 9 条全部实现并通过。实际落在新文件而不是 `client_test.cc`，
> 因为它要驱动真实 socket。实施中发现的库缺陷见提交 `bb1736e`。

依赖 **T3**。`test/client_test.cc`，需要能观察到"写出去的字节"。两种做法：

- 用 `loopback_broker` 变体，把收到的字节记录下来并断言；
- 或给 `connection` 加一个 `write_observer_for_test` 回调。

推荐前者，无需改库。

| 用例 | 输入 | 预期 |
|---|---|---|
| PublishQos1RetransmitsWithDup | 发 QoS1，broker 不回 PUBACK | 间隔到点后收到第二次 PUBLISH，`dup == true`，**packet id 不变** |
| PublishQos1GivesUpAfterThree | 同上，一直不回 | 第 3 次后 `finish_publish_failure` → 回调 `false`，`debug_pending_publish_count() == 0`，`on_close` 触发一次 |
| PublishQos1AckedStopsRetransmit | 发 QoS1，broker 立刻 PUBACK | 回调 `true` 一次；再等 2 个间隔仍无第二次 PUBLISH |
| PublishQos1DuplicateAckIgnored | 发 QoS1，broker 回两次 PUBACK | 回调只触发一次，不崩溃 |
| PublishQos2FullHandshake | 发 QoS2，broker 回 PUBREC | 客户端发 PUBREL(packet id 相同)；broker 回 PUBCOMP → 回调 `true` |
| PublishQos2PubrelRetransmits | 发 QoS2，broker 回 PUBREC 后不回 PUBCOMP | 间隔到点重发 PUBREL，最多 3 次后 `notify_closed_once()` |
| PublishQos2DupPubrecIgnored | broker 连发两个 PUBREC | 只发一个 PUBREL，不重复插入 `pending_pubrecs_` |
| PublishQos0WriteFailure | 连接已关 | 回调 `false`，`qos == 0`，`packet_id == 0` |

**注意**：`handle_pubrec` 在 `pending_publishes_` 命中时会新建 `pending_pubrec` 并覆盖已有条目（`pending_pubrecs_[pkt.packet_id] = entry;`）。`PublishQos2DupPubrecIgnored` 实际走的是"`pending_publishes_` 已删 → 命中 `pending_pubrecs_` → 直接 return"。写用例时确认走的是哪个分支。

|---|---|---|---|
| ConnackRefusedClosesSession | `handle_connack` 收到 rc=5 | `on_connect(false, 5)` 触发；`state() == disconnected`；`on_close` **不**触发 | 无 |
| ConnackSuccessMarksConnected | rc=0 | `on_connect(true, 0)`；`state() == connected` | 无 |

| PublishBackpressureRejects | 预置 1000 个 pending | 回调 `false`，日志含 backpressure | 无（或加 debug 钩子） |
| PacketIdExhausted | `next_packet_id_` 循环耗尽 | 回调 `false`，`notify_closed_once()` 一次 | 需要 hook 设初始值 |

| InboundPublishQos1WritesPuback | QoS1 PUBLISH | broker 收到 `0x40` + packet id | 无 |

### 需要改的库代码

**1. `async_subscribe_impl` 缺连接状态检查**（`client.hpp:661`）

```cpp
inline void mqtt_client::async_subscribe_impl(...) {
    if (closed_) { ... return; }
    if (qos > 2) { ... return; }
    // ← 这里少了 conn_->state() != connected 的判断
    uint16_t packet_id = acquire_packet_id();
```

对比 `async_publish_impl:602` 有这段。结果：握手未完成时订阅会把 SUBSCRIBE 排队，而 publish 会立刻拒绝。**两个 API 行为不一致**，且排队后 `pending_subscribes_` 不会在 CONNACK 失败时被清理（`notify_closed_once` 会清，但 `closed_ = false` 的路径不会）。

建议补上和 publish 一致的检查，并在 `handshaking` 状态下也拒绝。这会改变现有行为，但属于修正不一致。

**2. `handle_suback` 的检查顺序**（`client.hpp:430-437`）

```cpp
if (!cb) {
    return;               // ← 提前返回，下面的校验永远不跑
}
if (pkt.return_codes.size() < filters.size()) {
    notify_closed_once();
    return;
}
```

`mqtt_helper` 恢复订阅时用的正是 `async_subscribe(..., nullptr)`，所以重连后的订阅恢复路径上，非法 SUBACK 会被静默忽略。把 `!cb` 的返回挪到校验之后即可。

**3. `acquire_packet_id` 的测试钩子**

需要一个 `debug_set_next_packet_id(uint16_t)`，以便构造耗尽场景（否则要塞 65535 个条目）。

## T6 · 修现有 `connection_test` 的 broker

> 已完成。broker 抽到 `test/loopback_broker.hpp` 共用，`stop()` 先 `shutdown()` 再 join。

`test/connection_test.cc:57-111` `loopback_broker`：

```cpp
void stop() {
    io_.stop();                    // 不会让阻塞的 accept() 返回
    if (thread_.joinable()) {
        thread_.join();            // 若客户端从未连上，这里永远挂住
    }
}
```

且 `sock` 是 `serve()` 的局部变量，`stop()` 时已经析构，而 `read_some`/`write` 是阻塞的同步调用，`io_.stop()` 对它们无效。

现在只有一个用例，它总能连上，所以没暴露。写 T2 的新用例时必然踩到。

### 需要改的代码（仅测试代码）

- `sock` 提升为成员，`stop()` 里先 `sock_.close(ec)` 再 `acc_.close(ec)`，最后 join；
- 加一个 `std::atomic<bool> stopped_`，让 `serve()` 的阻塞点能提前退出；
- 或者改用非阻塞 + `poll`，但改动更大。

同时建议把这个 broker 抽到 `test/loopback_broker.hpp` 共用，因为 T4 也需要一个能记录收到字节、能按脚本回复的 broker。
